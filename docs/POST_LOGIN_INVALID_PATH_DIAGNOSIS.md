# VoteHub Post-Login `Invalid path specified in request URL` Diagnosis

**Date:** 2026-08-20
**Deployment:** None
**Authentication/configuration changes:** None

## 1. Exact Source of Error

The exact text `Invalid path specified in request URL` is not present in the VoteHub application source, login component, middleware, Next.js configuration, or installed Supabase package source searched locally.

Therefore, the application is not explicitly constructing or throwing this message. It is most likely an error returned by the remote Supabase/Auth request or surfaced by the browser/network layer while the Supabase client is making a request.

## 2. Login Flow

The deployed flow is:

```text
app/auth/login/page.tsx
  -> components/auth/LoginForm.tsx
  -> supabase.auth.signInWithPassword({ email, password })
  -> router.push("/dashboard")
  -> middleware.ts evaluates /dashboard
  -> middleware calls Supabase auth.getUser()
  -> dashboard is allowed or the request is redirected to /auth/login
```

The login form does not call `redirect()`, `router.replace()`, `window.location`, `URL()`, or construct a callback URL.

The only post-auth navigation in the login form is:

```ts
router.push("/dashboard");
```

## 3. Authentication Result

The client code checks the result of `signInWithPassword`:

```ts
const { error } = await supabase.auth.signInWithPassword(...);

if (error) {
  throw error;
}

router.push("/dashboard");
```

If the reported message is rendered by the form's `serverError` block, Supabase returned the error before `router.push("/dashboard")` ran. In that case the failure is during Supabase authentication/request construction, not after authentication.

If the browser first requests `/dashboard`, authentication succeeded far enough for `router.push` to run. Middleware then calls Supabase `auth.getUser()` and can surface a related Supabase request error while validating the session. The source contains no other post-login path construction.

The supplied symptom alone does not prove which of these two Supabase calls returned the message; browser Network/console evidence would be needed to distinguish them. It does prove the application-generated redirect target is `/dashboard`.

## 4. Redirect Destination

Actual application-generated destination:

```text
/dashboard
```

Expected destination after successful password authentication:

```text
/dashboard
```

Middleware behavior for an unauthenticated or invalid session:

```text
/auth/login?redirectTo=/dashboard
```

No code path in the login form redirects to `/auth/callback`, `undefined`, an empty path, `localhost`, a filesystem path, or a URL based on `NEXT_PUBLIC_APP_URL`.

## 5. Relevant Source Files

- `app/auth/login/page.tsx`: renders the existing login form.
- `components/auth/LoginForm.tsx`: calls Supabase `signInWithPassword`, then `router.push("/dashboard")`.
- `src/lib/supabase/Client.ts`: creates the browser Supabase client from `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- `middleware.ts`: protects `/dashboard` and calls Supabase `auth.getUser()`; unauthenticated requests go to `/auth/login?redirectTo=<path>`.
- `next.config.js`: contains only the `/login` and `/Login` rewrites to `/auth/login`; it does not affect `/dashboard`.
- `auth/Callback/route.ts`: handles Supabase code callbacks, but it is not called by the password login form.

## 6. Relevant Environment Variable Names

The login flow directly depends on:

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`

The login flow does not reference:

- `NEXT_PUBLIC_APP_URL`
- `NEXT_PUBLIC_SITE_URL`
- `NEXTAUTH_URL`

`NEXTAUTH_URL` is referenced by the health endpoint only, not by Supabase password login or the post-login redirect.

The public Supabase URL must be the bare project origin expected by the Supabase client, not a manually appended API path such as `/auth/v1`, `/rest/v1`, or another route suffix. The actual value was not printed or inspected here.

## 7. Root Cause

No malformed redirect path exists in the VoteHub login code. The generated path is the valid relative path `/dashboard`.

The highest-confidence root cause is a Supabase request URL/configuration problem affecting either `signInWithPassword` or middleware's subsequent `auth.getUser()` call. The error text is not generated by the local route or navigation code. Verify the staging `NEXT_PUBLIC_SUPABASE_URL` value is the Supabase project URL in Vercel Preview and has no API-path suffix or accidental filesystem/localhost value. Also verify the public anon key is paired with that project.

This conclusion does not assert that a secret value is wrong; it identifies the only URL-bearing configuration used by the login flow and the exact calls that consume it.

## 8. Recommended Minimal Fix

Do not change authentication code or add a redirect system. First inspect the browser Network/Console result for the failing request and verify, by name only, the Vercel Preview variables:

```text
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
```

Confirm the Supabase URL is the bare project URL. Do not add `/auth/v1`, `/rest/v1`, `/dashboard`, or a Vercel path to it. Keep `NEXTAUTH_URL` and `NEXT_PUBLIC_APP_URL` out of this login diagnosis because the login code does not use them.
