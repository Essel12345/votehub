# Phase 15 Registration 401 Diagnosis

**Date:** 2026-08-22
**Endpoint:** `POST /api/auth/register`
**Scope:** Deployed staging request
**Deployment changes:** None

## 1. Exact Source of 401

The 401 is not generated by the VoteHub registration route, middleware, rate limiter, registration service, or the Supabase Auth call.

A safe POST with `{}` to the staging endpoint returned:

```text
HTTP 401
response: {}
Server: Vercel
```

The empty response and Vercel server header indicate that the request is being rejected by a Vercel deployment/access layer before the Next.js application handler returns its own response. The application route's 401-producing code paths were not reached.

## 2. File Responsible

No inspected application file returns this 401 for `POST /api/auth/register`.

The relevant application files are:

- `app/api/auth/register/route.ts` - invokes rate limiting, validates the body, and returns 400 or 201; it has no 401 response.
- `src/lib/security/rate-limit.service.ts` - returns 429 when limited and 503 when the production backend is unavailable; it has no 401 response.
- `src/services/auth.service.ts` - calls Supabase Auth and throws on failure; the registration route catches that error and returns 400.
- `middleware.ts` - does not match `/api/auth/register`.

The responsible layer is therefore the deployed Vercel access/protection configuration or another platform-level gate outside this repository.

## 3. Middleware Behavior

The active `middleware.ts` matcher contains:

```text
/dashboard/:path*
/admin/:path*
/settings/:path*
/organizations/:path*
/elections/:path*
```

It does not match `/api/auth/register`. Its `protectedRoutes` list likewise contains dashboard, admin, settings, organizations, and elections paths, but not the registration API.

When middleware does run, it calls `supabase.auth.getUser()` only for those protected paths and redirects unauthenticated users to `/auth/login`. It does not return a 401 for registration, redirect the registration request, or rewrite its pathname.

## 4. Registration Authentication Method

The registration service uses:

```ts
adminClient.auth.admin.createUser({
  email,
  password,
  email_confirm: true,
  user_metadata: { ... },
});
```

It does not use `supabase.auth.signUp()`. This call occurs only after rate limiting and schema validation. No Auth call can produce the observed empty Vercel 401 before the application handler runs.

## 5. Whether Supabase Is Reached

No. The staging request is rejected with HTTP 401 and an empty response at the Vercel layer. The VoteHub route does not reach `registerOrganization()`, and therefore does not reach `adminClient.auth.admin.createUser()` or the later organization/profile database writes.

This conclusion is based on the response shape and platform header plus the complete local route trace. No Supabase keys, Auth tokens, cookies, or passwords were inspected or printed.

## 6. Whether Rate Limiting Succeeds Before the 401

The request does not reach the application rate limiter. `applyRateLimit()` is the first statement inside the registration handler, but the platform-level 401 occurs before that handler executes.

The application would return:

- HTTP 429 for a valid rate-limit counter that exceeds the `REGISTER` limit;
- HTTP 503 for a rate-limit configuration/backend exception in production;
- HTTP 400 for invalid registration JSON/schema or downstream registration errors;
- HTTP 201 after successful registration.

It does not return HTTP 401 from this route.

## 7. Relevant Environment Variable Names

Application variables relevant to registration and rate limiting are:

- `NEXT_PUBLIC_SUPABASE_URL` - public client configuration;
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` - public client key;
- `SUPABASE_SERVICE_ROLE_KEY` - server-only key used by `adminClient.auth.admin.createUser()`;
- `RATE_LIMIT_BACKEND` - server-only backend selector;
- `UPSTASH_REDIS_REST_URL` - server-only Upstash endpoint;
- `UPSTASH_REDIS_REST_TOKEN` - server-only Upstash secret.

These names do not explain the observed 401 response. Missing rate-limit variables produce the documented production 503, not 401. No actual environment values were printed or exposed.

## 8. Root Cause

The staging deployment is protected by a Vercel-level access/deployment protection mechanism, or an equivalent Vercel project setting, that rejects the unauthenticated request with HTTP 401 before Next.js routing. This is separate from Supabase authentication and the application's middleware.

The test request used no Vercel protection bypass credential, no Authorization header, no cookies, and no user credentials. Consequently, the platform rejected it before the public registration API could execute.

Vercel deployment logs were not available through this workspace, so the platform's internal protection rule name cannot be confirmed here. The Vercel project/deployment settings and request logs should be checked for Deployment Protection, Vercel Authentication, password protection, or an access-control integration.

## 9. Minimal Secure Fix

Keep application authentication and rate limiting unchanged. In Vercel, configure the staging deployment so the public registration endpoint is reachable without a Vercel deployment-protection credential, or use the approved Vercel staging access procedure for authorized testers. Apply the narrowest project/path access policy available and keep production protection unchanged.

Do not add an application bypass, hard-code credentials, disable Supabase Auth, disable rate limiting, or modify the database. After the Vercel access setting is corrected, repeat a safe POST and expect the application-level response, such as HTTP 400 for `{}`; then test a valid synthetic registration only when an approved test account/data plan is in place.
